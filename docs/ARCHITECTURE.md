# 架构设计文档

## 1. 总体架构

```
┌─────────────────────── 用户设备（可信区）───────────────────────┐
│  网页前端 / 移动 APP（同一套 Web 代码，Capacitor 封装移动端）      │
│  ┌────────────┐   ┌──────────────┐   ┌──────────────────────┐  │
│  │ 块级编辑器  │   │ 本地加密引擎   │   │ 本地明文缓存+搜索索引  │  │
│  │ [[双链]]图谱│──▶│ PBKDF2→AES-GCM│◀─│ IndexedDB（明文）     │  │
│  └────────────┘   └──────┬───────┘   └──────────────────────┘  │
└──────────────────────────┼─────────────────────────────────────┘
                    只有密文经过这里（HTTPS）
┌──────────────────────────▼─────────────────────────────────────┐
│        零知识后端（Docker 容器，Node.js + SQLite）               │
│  账号服务(OAuth) │ 密文同步 API │ WebDAV 哑管道中继 │ 静态托管    │
│  ❌ 无密钥  ❌ 无解密逻辑  ❌ 不落任何明文                        │
└─────────────────────────────────────────────────────────────────┘
```

## 2. 技术选型与理由

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | Node.js 24 + Express | 单依赖、单容器，资源占用极小；服务器逻辑极薄正是零知识架构的优势 |
| 数据库 | SQLite（node:sqlite 内置） | 私有部署单实例场景下，SQLite 零运维、零原生编译依赖；WAL 模式支撑并发读写。数据量到百万级密文块毫无压力 |
| 加密 | WebCrypto：PBKDF2-SHA256(310000 轮) → AES-256-GCM | 浏览器原生支持、经过大量审计；GCM 提供认证加密（防篡改）。生产演进方向：替换为 Argon2id（见安全文档） |
| 前端 | 原生 ES Module + 无构建链 | 前端越简单越可审计——加密代码的可审计性本身就是安全特性 |
| 移动端 | Capacitor | 复用同一套 Web 代码，iOS/Android 一份工程 |
| 部署 | Docker Compose | 一键拉起，数据卷持久化 |

## 3. 数据模型

**服务器（只见密文）：**

- `users`：id / email / google_sub / kdf_salt（盐是公开参数）——不含任何机密
- `blobs`：`(user_id, id, type, nonce, cipher, deleted, client_updated_at, rev)` — type 只有 `note`/`verifier`，cipher 是 AES-GCM 密文，服务器不可读
- `sync_log`：同步审计记录（只有 blob id 与时间，无内容）
- `sessions`：登录会话令牌（仅标识身份）

**客户端（明文，仅本地）：**

- 笔记对象：`{ id, title, blocks[{id,type,html}], tags[], createdAt, updatedAt, deleted }`
- IndexedDB 缓存明文笔记；内存中维护搜索索引与双链图谱

## 4. 同步协议

1. 客户端每次保存笔记：本地改 → 加密 → `POST /api/sync/push`；
2. 服务器为每个 blob 分配**每用户单调递增 rev**，作为同步游标；
3. 客户端启动/恢复时 `GET /api/sync/pull?since=<本地游标>`，拉到密文后逐条本地解密；
4. 冲突策略：**last-write-wins**（比较 `client_updated_at`）。块级编辑粒度 + 单用户为主的设计下，此策略实现简单且足够；后续可演进为块级 CRDT。

## 5. 关键设计决策

- **为什么谷歌 OAuth 与加密解耦？** OAuth 只回答"你是谁"，加密回答"谁能看"。两者分离意味着：即使将来更换身份提供商，已加密数据依然可用。
- **为什么 KDF 盐存服务器？** 盐不是机密，存服务器可让用户在任意新设备上派生同一密钥（否则换设备金库无法恢复）。
- **为什么 WebDAV 中继而不是客户端直传？** 浏览器跨域限制使直连第三方 WebDAV 常被 CORS 拦截；服务器做哑管道（只转发字节流），密文先在客户端生成，中继全程不可读，兼得可用性与零知识。
- **为什么 Verifier 存服务器？** 加密的固定校验串，用于新设备验证主密码正确性，同时不泄露任何内容（AES-GCM 认证解密失败即密码错误）。

## 6. 目录结构

```
fairy-notes/
├── docker-compose.yml / Dockerfile / .env.example
├── server/
│   ├── package.json
│   └── src/
│       ├── index.js    # 入口：路由、登录、静态托管
│       ├── db.js       # SQLite 表结构与迁移
│       ├── auth.js     # OAuth 校验、会话管理
│       ├── sync.js     # 密文 pull/push
│       └── webdav.js   # WebDAV 哑管道中继
└── web/
    ├── index.html / css/app.css
    └── js/
        ├── crypto.js   # PBKDF2 + AES-GCM（本地）
        ├── store.js    # 本地金库 + 同步引擎
        ├── api.js      # 后端通信封装
        ├── webdav.js   # 客户端加密备份
        ├── graph.js    # 知识图谱
        └── app.js      # 主应用逻辑
```
